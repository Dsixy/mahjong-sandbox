# 引擎架构与格式

## 模块职责

| 模块 | 职责 |
|---|---|
| `tiles.py` | 34 牌种编号、136 范围实体 ID、川麻 108 张库存、紧凑记法 |
| `hands.py` | 无计分规则的普通和型全部拆解、七对结构、结构听牌 |
| `model.py` | 版本化配置、动作、阶段、副露、牌河、事件、赢家、账本 |
| `scoring.py` | 本版本川麻胡牌资格、最优计分、查大叫候选 |
| `engine.py` | 本版本川麻流程、原子响应裁决、可见性和不变量 |
| `agents.py` | 只读取玩家观察的随机基线、完整局运行器 |
| `replay.py` | 完整裁判牌谱及确定性验证 |
| `cli.py` | 无界面模拟与回放命令 |
| `riichi_model.py / riichi_engine.py` | 四人立直配置、单局流程、王牌、振听及结算 |
| `riichi_scoring.py / riichi_agent.py` | 日麻和型、役、符、点数和可见信息牌效基线 |
| `riichi_match.py` | 东风/半庄推进、终止与整场回放 |

目前 `Engine` 是第一种麻将的参考流程。`RiichiEngine` 使用独立行牌及结算流程，共享牌、序列化及适合共享的和型算子；不会在血战循环里硬编码大量日麻条件。前端、RL 环境及优化后端都应保持 `observe / legal_actions / submit` 的动作语义一致。

## 牌与手牌

```text
kind = tile_id // 4
copy = tile_id % 4
0..8 万，9..17 筒，18..26 索，27..30 东南西北，31..33 白发中
川麻 tile_id = 0..107；共享牌辅助函数可识别 0..135
```

实体 ID 是库存的身份，不是神经网络的直接特征。暗手实体牌列表是权威数据，`counts_of()` 派生不可变 34 长度计数。副露是另一独立位置。日麻赤牌配置映射在实体 ID 属性上，不能改变基础牌种含义。

副露记录类型、牌 ID、来源玩家、被鸣牌；加杠额外记录补上的实体牌。牌河记录弃牌 ID、摸切标记、被鸣玩家和荣和引用。赢家的 `Win.tile` 是引用：多家荣和共享同一弃牌，不能复制一张牌到多位赢家暗手中。被抢的第四张保存在 `robbed_tiles`；抢杠后原碰不变。

`hand_effective_count = len(concealed) + 3 * len(melds)`。活跃玩家等待时为 13，自家决策为 14；自摸赢家实际持有 14，荣和赢家持有 13 加一条和牌引用。杠的第四张不计入这个结构计数，但仍计入实体库存。

## 决策与动作

阶段为 `exchange / declare_suit / self_turn / discard_response / rob_kong_response / terminal`。每个新决策窗口递增 `decision_id`，每个接受的命令递增 `revision`。一个窗口有固定响应者集合，各方只能提交一次。过期 ID、错误玩家和非法动作均在修改状态前拒绝。

动作 JSON 有固定字段：

```json
{"kind":"added_kong","tiles":[16],"suit":null,"meld_index":0}
```

`tiles` 只包含该玩家将消耗的暗牌；被鸣的弃牌由待裁决窗口指定。实体牌 ID 要排序、唯一；`declare_suit` 单独指定 `suit`，`added_kong` 单独指定 `meld_index`，其他动作不能夹带无关参数。合法动作是结构化候选列表，目前不定义训练专用全局动作编号。

没有网络、时钟、UI 或模型进入核心循环。`submit()` 在响应未收齐时仅保存密封请求；收齐后执行裁决并推进到下个决策点。它返回事件和本次分数变化。普通摸牌、杠补牌等自动步骤由引擎完成。

## 信息隔离

`State`、完整事件、`Transition` 和回放只供可信裁判。`observe(player)` 提供自己的暗牌和过胡状态、对手暗牌张数、已胡公开暗牌、公共副露/牌河/分数、自己的合法动作及过滤事件，不含牌墙、种子、交换前的方向、其他方的密封选择。

公共摸牌事件显示玩家、牌源和剩余张数，实际牌 ID 只在摸牌玩家的私有事件字段中。定缺和换牌选择全部收齐后才产生公开效果。服务层必须用 `Transition.for_player(player)` 过滤事件；直接序列化完整 Transition 会泄露裁判信息。返回对象使用拷贝，修改观察不能改变裁判状态。

## 不变量

构造游戏及每次接受命令后，`assert_invariants()` 验证：

- 未摸牌墙 + 所有暗手 + 所有副露 + 未被鸣走的弃牌 + 被抢牌，恰好是 108 个实体各一次。初始牌墙、被鸣的牌河记录、Win 是历史/引用，不重复计数。
- 暗牌及副露面子对应的结构张数正确；副露牌种统一、张数正确、没有缺门副露。
- 被鸣牌河记录能指向实际拥有实体牌的副露；摸牌标记指向该玩家持有的牌。
- 赢家唯一、不继续行牌；不向已胡玩家发新请求；终局有结束原因且没有响应者。
- 分数与逐笔支付账本一致，总分始终为 0，交易金额为正且双方不同。

这是一份可检查的参考实现，优先规则正确性，不以当前深拷贝与 Python 列表作为未来性能实现的限制。数组/原地更新后端可替换存储，但必须保持动作语义、不变量和回放结果。

## 确定性与回放

洗牌和换牌方向只使用引擎初始化的局部随机源；策略使用各自独立随机源。初始化后，核心流程不再调用随机数。

回放格式 v1 保存引擎版本、完整规则配置、种子、完整初始牌墙、交换方向、按提交顺序的动作以及预期完整状态/事件 SHA-256。直接保存牌墙可避免依赖不同 Python 版本的随机算法实现。重放从构造游戏开始逐条校验合法性，最后比较状态、事件、分数、结束原因和命令数。完整和部分牌谱都可验证；版本不兼容或被修改的牌谱会报错。

回放包含隐藏信息，不应作为在线策略输入。已发生的公开事件可以从玩家投影获得；完整牌谱用于调试、离线分析和后端差分检查。

## 验收证据

`tests/` 包括确定值的和型/计分用例、库存有效的定向局面、响应优先级及到达顺序、各类杠和抢杠、过胡、结算、非法输入、隐私投影、完整/部分/文件回放与篡改检测。局面构造器只用于测试，不是生产开局接口。

`scripts/validate_random.py` 额外执行大量从真实发牌开始的完整随机牌局，混合开关和庄家座位，每步检查不变量，并抽样保存后重放验证。阶段 1 和阶段 2 的验收要求均在该文档和规则定义的范围内。

阶段 3 的 `webserver.py` 通过同一 `observe / legal_actions / submit` 接口驱动浏览器牌桌，`greedy.py` 提供可见信息牌效基线。前端只显示玩家投影，所有规则和分数仍由引擎计算。接口、隐私边界、回放检查点和素材说明见 [WEB.md](WEB.md)。阶段 4 的日麻流程、番符算子、对局控制器和共享回放协议见 [RIICHI.md](RIICHI.md)。并发向量化与 RL 留待后续阶段。
